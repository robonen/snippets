# 07. Права и криптография

> **Статус (2026-08-25): конфиденциальность реализована** — `src/crypto/`:
> секрет ленда 16 Б (= `gift.code`; §4 обещал AES-256, формат сильнее — живём
> на AES-128-GCM), `sealPack`/`openPack` (печать payload санда; нонс 12 Б
> выводится из `landId ‖ tag ‖ time ‖ tick ‖ peer ‖ self ‖ head ‖ lead`, связка
> целиком в AAD; расшифровка на ГРАНИЦЕ хранилища/провода, память ленда
> открытая — см. `sealedStore`), ECDH-идентичность с `mutual` (CTR, под
> `gift.code`) и `mutualSealed` (GCM, под обёртки произвольной длины).
>
> **Аутентичность тоже реализована** — `signer.ts`/`rank.ts`/`signed.ts`:
> Ed25519 (fallback ECDSA P-256) подписант и проверяльщик; `Seal` над хэшами
> запечатанных юнитов с привязкой к ленду (encrypt-then-sign) и PoW-майнингом
> `tick` под `rate`; `Pass` как публичный ключ; `signPack`/`verifyPack` на
> границе пачки (инкрементально — не пере-подписывают покрытое); tier/rate из
> `rank.ts`. `Land` хранит seal/pass/gift плоским набором-спутником графа
> (`#extra`) и ретранслирует их — иначе печати не пережили бы сервер-релей.
> Что ОСТАЁТСЯ проектом: `rankAudit` (чистка при понижении прав), групповые
> ключи и ротация — разделы 5, 8 ниже.

Пакет `@sync/crypto` поверх WebCrypto. Работает в браузере, Node ≥ 20 и воркерах
без полифилов.

## 1. Ранг — один байт

```
 7 6 5 4   3 2 1 0
└─ tier ─┘ └─ rate ─┘
```

### Tier — уровень доступа

| Значение | Имя | Что можно |
|---|---|---|
| `0b0000` | `deny` | ничего |
| `0b0001` | `read` | читать |
| `0b0011` | `post` | писать данные |
| `0b0111` | `pull` | писать данные и метаданные (сливать форки) |
| `0b1111` | `rule` | всё, включая раздачу прав |

Биты вложенные, поэтому проверка — `tier(peer) >= unit.tierMin()`, одно сравнение.

### Rate — сложность записи (PoW)

| Имя | Нулевых бит | Порядок задержки |
|---|---|---|
| `just` | 0 | микросекунды |
| `fast` | 8 | миллисекунды |
| `slow` | 11 | полсекунды |
| `long` | 12 | секунды |
| `late` | 15 | дни |

**Скорость записи — это право.** Антиспам встроен в модель доступа, а не
прикручен сбоку на сервере. Пир с рангом `post:late` формально может писать, но
каждая запись стоит ему заметного CPU.

По умолчанию — `just`, то есть выключено
([ADR-009](00-decisions.md#adr-009--proof-of-work-выключен-по-умолчанию)).

## 2. Ключи и идентичность

```ts
export interface Identity {
  peer: Link                                   // SHA-256(pub)[0..8)
  pass: Pass                                   // публичный ключ как юнит
  sign(data: BufferSource): Promise<Uint8Array>
  verify(data: BufferSource, sign: BufferSource, pass: Pass): Promise<boolean>
  secretMutual(other: Pass): Promise<CryptoKey>    // ECDH → HKDF → AES-GCM ключ
}
```

- Подпись: **Ed25519**, где доступен (Safari 17+, Chrome 137+, Node 20+),
  иначе **ECDSA P-256**. Выбор фиксируется в первом байте `Pass`.
- Обмен ключами: **X25519** / **ECDH P-256** соответственно.
- Симметричное: **AES-GCM-256**.

Приватный ключ хранится в `localStorage`/`IndexedDB` как **неэкспортируемый
`CryptoKey`**, где платформа это позволяет. Это лучше, чем в baza, где ключ лежит
строкой в `localStorage` и доступен любому XSS.

## 3. Seal — подпись пачками

Подписывается не каждый юнит, а `Seal` — список из ≤ 10 хэшей:

```
Seal { peer, time, tick, hashes[≤10], sign }
```

Юнит считается достоверным, если существует `Seal` того же пира, содержащий его
хэш. Когда часть юнитов из пачки умирает (перезаписаны LWW), `Seal` живёт, пока
жив хотя бы один его элемент (`aliveItems`); когда последний уходит — `Seal`
удаляется вместе с ним.

Выигрыш: 1 операция ECDSA на 10 изменений вместо 10.

### PoW внутри подписи

```ts
do {
  seal.timeTick(clock.tick())                 // меняем nonce
  const sens = xor(seal.shot(), land.id)      // подмешиваем id ленда
  sign = await identity.sign(sens)
} while (leadingZeroBits(sign) < rateBits)
```

Подмешивание `land.id` через XOR — защита от переноса подписи в другой ленд.

Считается в **отдельном воркере** с поддержкой отмены и прогресса:

```ts
export interface PowWorker {
  mine(seal: Seal, bits: number, signal: AbortSignal): Promise<Uint8Array>
  onProgress(cb: (attempts: number) => void): void
}
```

## 4. Шифрование ленда

Если пиру `null` (то есть «всем») не выдан `read`, ленд шифруется:

```
секрет ленда S (AES-256, случайный)
для каждого пира P с правом read:
    K = HKDF(ECDH(мой_приватный, P.pub))
    gift[P].code = AES-GCM(S, key = K, iv = gift.salt)
```

Читатель восстанавливает `S` из своего `gift`, расшифровав его взаимным ключом.
Сервер-релей **не может** прочитать данные — он видит только зашифрованные
`payload` и открытые метаданные (кто, когда, куда в графе).

### Важное отличие от baza

В baza расшифровка ленивая — `sand_open()` вызывается при чтении и приостанавливает
файбер. Мы можем оставить так же (файберы у нас есть!), но **по умолчанию
расшифровываем на входе**, в `applyPack`, батчем через `Promise.all`. Причины:

- меньше приостановок в горячем пути чтения;
- проще профилировать;
- батч из 500 расшифровок в разы быстрее 500 одиночных.

Ленивый режим оставляем опцией для лендов с большими блобами.

### Границы гарантии

Отзыв `read` **не отзывает уже прочитанное**. Если пир сохранил себе ключ или
данные, пока доступ был, — они у него остались. Это надо написать в доке жирным:
`rankAudit()` чистит только локальное состояние узлов, которые честно соблюдают
протокол.

## 5. `rankAudit` — чистка при понижении прав

```ts
rankAudit() {
  restart: while (true) {
    for (const seal of seals) if (rank(seal.peer) < seal.rankMin()) drop(seal)
    for (const gift of gifts) if (tier(gift.peer) < gift.tierMin()) { drop(gift); continue restart }
    for (const sand of sands) if (tier(sand.peer) < sand.tierMin()) drop(sand)
    break
  }
}
```

Цикл с рестартом нужен, потому что удаление `gift` меняет права других пиров —
каскад. Порт [land.ts:661](../../baza/land/land.ts#L661).

## 6. `trusted` — не проверять своё

`WeakSet<Unit>` для юнитов, которым верим без проверки подписи:
- созданные локально;
- прочитанные из собственного хранилища;
- пришедшие по внутренней шине вкладок того же origin.

Экономит тысячи операций ECDSA при старте приложения. Порт
[unit.ts:20](../../baza/unit/unit.ts#L20).

⚠️ Ровно одна ошибка здесь = дыра в безопасности. Тест `crypto.trusted.boundary`:
юнит, пришедший из сети, **никогда** не попадает в `trusted` до проверки.

## 7. Тесты

| Тест | Что |
|---|---|
| `crypto.sign.roundtrip` | подпись/проверка на обоих алгоритмах |
| `crypto.tamper` | изменённый байт юнита → подпись не проходит |
| `crypto.replay` | подпись из ленда A не принимается в ленде B |
| `crypto.pow` | подпись с `rate=fast` действительно имеет ≥ 8 нулевых бит |
| `crypto.pow.abort` | отмена майнинга не оставляет висящий воркер |
| `crypto.secret` | два пира независимо выводят одинаковый взаимный ключ |
| `crypto.encrypted` | без `gift` ленд нечитаем; с `gift` — читаем |
| `rights.demote` | понижение до `read` убирает все записи пира |
| `rights.cascade` | понижение `rule`→`read` каскадно убирает выданные им права |
| `crypto.trusted.boundary` | сетевой юнит не попадает в `trusted` без проверки |

## 8. Что отложено

- **Ротация ключей.** Сейчас `peer` = хэш ключа, смена ключа = смена личности.
  Решение (`Pass` со ссылкой на предыдущий + подпись преемственности) — за рамками MVP.
- **Групповые ключи.** Раздача секрета каждому пиру персонально — O(N) гифтов.
  Для больших групп нужен key-tree; отложено.
- **Post-quantum.** Не сейчас, но `Pass` версионируется первым байтом, так что
  место оставлено.

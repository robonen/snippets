# 03. Бинарный формат

Три сущности: `Link` (идентификатор), `Unit` (юнит), `Pack` (контейнер).
Плюс `Vary` — детерминированный кодек значений.

Правило номер один: **формат — публичный контракт с первого релиза**
([ADR-005](00-decisions.md#adr-005--один-бинарный-формат-для-провода-диска-и-дампа)).
Любое изменение офсетов ломает данные у пользователей и сеть между версиями.

---

## 1. Link — идентификатор

```
peer(8) _ area(8) _ head(6)
└── lord ─┘
└──── land ───────┘
└──────── pawn ──────────┘
```

| Уровень | Байт | Что |
|---|---|---|
| `peer` | 8 | первые 8 байт SHA-256 публичного ключа ([ADR-007](00-decisions.md#adr-007--peer--8-байт-land--16-байт)) |
| `area` | 8 | под-ленд; нули = домашний ленд лорда |
| `head` | 6 | локальный id пешки внутри ленда |

Текстовое представление — **стандартный** base64url без паддинга (RFC 4648 §5),
секции через **точку**, нулевые секции опускаются:
`AQIDBAUGBwg`, `AQIDBAUGBwg.ERITFBUWFxg`, `AQIDBAUGBwg..ISIjJCUm`.

Разделитель именно точка, а не `_`: подчёркивание — 63-й символ base64url, и с ним
разбор неоднозначен ([ADR-014](00-decisions.md#adr-014--текст-ссылки-стандартный-base64url-разделитель--точка-)).
Длины секций при 8/8/6 байтах — 11/11/8 символов.

```ts
export class Link {
  readonly bin: Uint8Array          // 8 | 16 | 22 байта
  readonly str: string              // кэш текстового вида
  static peer(bin): Link
  static land(peer, area): Link
  static pawn(land, head): Link
  static hash(bin: BufferSource): Link       // первые N байт SHA-256
  peer(): Link; area(): Link; head(): Link; land(): Link; lord(): Link
  relate(base: Link): Link        // абсолютный → относительный внутри ленда
  resolve(base: Link): Link       // относительный → абсолютный
  xor(other: Link | Uint8Array): Uint8Array   // для подмешивания в подпись
}
```

`relate`/`resolve` — прямой порт из [link.ts](../../baza/link/link.ts): ссылка
внутри своего ленда хранится в 6 байтах, а не в 22. Экономия ~70 % на графах
связей внутри документа.

## 2. Unit — юнит

Юнит — **вид над `ArrayBuffer`**, а не JS-объект: поля читаются по офсетам, а не
копируются в поля объекта. Причины: хэш считается по точным байтам; на диск и в
сокет уходит memcpy; 100k юнитов — это 100k `ArrayBuffer` без графа объектов для GC.

Чтение big-endian — **ручное, не через `DataView`**. Замер (`bench/unit.mjs`):
`getUint32` 2.8 нс против 4.3 нс у ручного чтения, но создание вида — 58.6 нс и
+48 Б на юнит. Вид окупается с двадцатого чтения одного и того же юнита, а
платится на каждом разобранном — включая те, что не переживут LWW-свёртку.

### Общая часть (все виды)

```
off  len  поле        примечание
0     1   kind        1=sand 2=gift 3=seal 4=pass
1     1   meta        для sand: tag(2 бита) | inlineSize(6 бит)
2     4   time   BE
6     2   tick   BE
8     8   peer
```

Порядок сравнения (LWW): `time ↓, peer ↑, tick ↓` — как в
[unit.ts:96](../../baza/unit/unit.ts#L96).

> **Сравнение — пополевое. `memcmp` здесь невозможен.** Ранняя редакция этого
> раздела обещала «14 байт компаратора подряд, сравнение сводится к `memcmp`».
> Обещание неверно по трём независимым причинам:
> 1. `time` идёт по убыванию, а `memcmp` — по возрастанию;
> 2. `tick` физически лежит **перед** `peer`, а по приоритету идёт **после**;
> 3. направления смешаны (`↓ ↑ ↓`), поэтому и обратный `memcmp` не спасает —
>    он верен на полях, идущих по убыванию, и неверен на `peer`.
>
> Перестановка полей не помогает: понадобилось бы хранить `~time` и `~tick`
> и держать `tick` после `peer` — то есть класть на диск дополненные до единицы
> числа ради выигрыша, которого нет (пополевое сравнение — 11.8 нс при бюджете
> 40 нс, сортировка 1000 юнитов лишь на 21 % медленнее сортировки обычных
> объектов). Контрпример на каждый из трёх пунктов держит тест
> `обещание спецификации про memcmp 14 байт НЕ выполняется`.

> **Арбитраж по пиру определён на БАЙТАХ, а не на тексте ссылки.** base64url
> ставит цифры после букв, а `-`/`_` — до цифр в ASCII, поэтому текстовый
> порядок ссылок не совпадает с байтовым, и это не абстракция: пиры `0xf4…` и
> `0xf8…` дают `"9AAAAAAAAAA"` и `"-AAAAAAAAAA"`, то есть по байтам первый
> меньше, а по тексту — больше. Оба порядка детерминированы, но это **разные**
> полные порядки, и на конкурентных правках они выбирают разных победителей.
> Следствие для слоя ленда ([04](04-crdt-core.md)): пока `Sand.peer` — строка,
> в ней допустима только сохраняющая порядок кодировка (hex), а при переезде на
> бинарный юнит сравнение обязано идти через `Unit.compare`. См. ADR-015.

### Sand — данные

```
16    6   self        собственный id
22    6   head        родитель (0 = корень ленда)
28    6   lead        предыдущий сосед (0 = начало списка)
34    2   sizeBig     если inlineSize == 63
36   12   shot        SHA-256[0..12) от ball — если big
48    …   payload     inline, ≤ 62 байта, выравнивание до 8
```

`inlineSize` — 6 бит, то есть 0…63, но значение **63 занято маркером** «значение
вынесено в ball». Поэтому потолок inline — 62 байта, а не 63: ранняя редакция
противоречила сама себе, обещая «≤ 63 байт» и тут же «sizeBig если
inlineSize == 63».

`tag` — 2 бита: `term` (само значение) · `solo` (регистр) · `vals` (список) ·
`keys` (словарь). Именно он позволяет одному формату хранить регистр, список,
словарь, текст и DOM ([05](05-model-api.md)).

Большие значения (> 62 байт) выносятся в отдельный `ball`, в юните остаётся
12-байтовый хэш. Так юнит остаётся фиксированного размера, а `ball` можно не
грузить, пока не понадобится.

### Gift — права и ключ

```
16    8   mate        кому выданы права (0 = всем)
24    1   rank        tier(4 бита) | rate(4 бита)
32   16   code        секрет ленда, зашифрованный взаимным ключом
```

### Seal — подпись пачки

```
1     1   meta        count(4 бита) | wide(1 бит)
16    …   hashes      count × 12 байт
…    64   sign
```

### Pass — публичный ключ

```
16    …   key         сырой ключ, длина по алгоритму; общая часть — как у всех
```

Паспорт носит **ту же 16-байтовую общую часть**, что и остальные виды, а не
является сырым ключом, как обещала ранняя редакция. Три независимые причины:

1. Диспетчер разбора читает вид из байта 0. У сырого ключа этот байт — часть
   ключа: у несжатой точки P-256 там `0x04` (совпало с кодом `pass` случайно), у
   Ed25519 — произвольный байт. baza выкручивалась перебором ключей, у которых
   первый байт равен `0xFF`, — то есть PoW ради разбора.
2. [07 §2](07-crypto-rights.md) требует хранить в первом байте выбор алгоритма —
   а он же занят видом.
3. `peer` — это SHA-256 ключа, и без заголовка он считается только асинхронно;
   тогда `path()` паспорта не может быть синхронным, как у остальных видов.

Восемь байт `peer` в общей части паспорта избыточны — и это **не** повод им
верить: проверка ключа обязана пройти до того, как паспорт куда-то принят.

### API

```ts
export abstract class Unit {
  readonly buf: Uint8Array
  kind(): UnitKind
  time(): number; tick(): number; peer(): Link
  hash(): Promise<Uint8Array>        // SHA-256[0..12) от всего буфера, кэшируется
  static compare(a?: Unit, b?: Unit): number
  static parse(buf: Uint8Array): Unit      // диспетчер по kind
  path(): string                     // ключ в хранилище: 'sand:head/peer/self'
}
```

`hash()` возвращает не `Link`, как обещала ранняя редакция, а 12 сырых байт, и
асинхронно. Два независимых основания: 12 байт не входят в канонический набор
длин ссылки (`0/8/16/22` по ADR-014), а `crypto.subtle.digest` асинхронен по
контракту WebCrypto — синхронного SHA-256 в браузере нет, и городить свой ради
одной подписи значит завести вторую реализацию хэша, которую придётся сверять с
первой.

**Инвариант:** после создания юнит иммутабелен. Все конструкторы — статические
фабрики, собирающие буфер целиком; сеттеров нет.

## 3. Pack — контейнер

```
┌ Land-заголовок ────────────────────────────────┐
│ "LAND" (4) │ landId (16) │ faceCount (2) │ pad │
├ Faces ─────────────────────────────────────────┤
│ peer(8) tick(2) time(4) summ(4) pad(6)  × N    │
├ Units ─────────────────────────────────────────┤
│ unit … [ball …] × M                            │
└────────────────────────────────────────────────┘
   (далее может идти следующий Land-заголовок)
```

Секции выровнены на 8 байт — **именно это делает файл хранилища одновременно
ареной аллокатора** ([06](06-storage.md)): удалённый юнит зануляется, его слот
помечается свободным (`kind = 0`), парсер такие слоты пропускает.

Семантика пакета зависит от наполнения:

| Faces | Units | Смысл |
|:---:|:---:|---|
| ✓ | ✗ | «вот моё состояние» — начало синхронизации |
| ✗ | ✓ | дельта |
| ✓ | ✓ | дельта + подтверждение состояния |
| ✗ | ✗ | «забудь этот ленд» — отписка |

```ts
export function packEncode(parts: Iterable<[LandId, PackPart]>): Uint8Array
export function packDecode(buf: Uint8Array, opts?: {
  offsets?: WeakMap<AnyUnit, number>           // для арены: где лежит каждый юнит
  pool?: MemoryPool                            // регистрация занятых слотов
}): Array<[LandId, PackPart]>
```

Ключ `offsets` — **юнит, а не `ArrayBuffer`**, как требовала ранняя редакция.
Юнит у нас — окно в буфер пачки, а не копия, поэтому `ArrayBuffer` у всех юнитов
пачки один: ключ-буфер дал бы либо одну запись на всю пачку, либо копию каждого
юнита — ровно то, ради ухода от чего затеян бинарный формат.

### Открытый вопрос: большой санд без приложенного `ball`

[§2](#2-unit--юнит) обещает, что `ball` «можно не грузить, пока не понадобится» —
ради этого в юните и лежит 12-байтовый `shot`. Но формат пачки этого не выражает:
после большого санда парсер **обязан** прочесть `align8(sizeBig)` байт, потому что
маркера «балл не приложен» в раскладке нет. Сейчас кодек считает такой санд
ошибкой кодирования — честнее, чем в baza, где `length()` считал размер по
`sand.ball()`, а `make()` писал по `sand.size()`: при незагруженном балле буфер
выделялся короче, чем в него писали, хвост молча обрезался, а следующий юнит
уезжал на место балла.

Развилка на [S7](11-roadmap.md), где требования протокола станут конкретными:
свободные биты есть в байте `kind` (значения 1…4, старшие биты не заняты), и
пометка «балл отделён» естественно ложится туда — но решать это стоит вместе с
тем, как узел запрашивает недостающие баллы, а не раньше.

## 4. Vary — кодек значений

Поддерживаемые типы (по образцу [vary.ts](../../baza/vary/vary.ts)):

`null · bool · int · bigint · float · string · bytes · Link · Date · Duration ·
Interval · array · map · tree`

Вещественные пишутся как **8 байт float64 в big-endian**, без укорочения до float32.
Порядок байт совпадает с остальными многобайтовыми полями формата, а укорочение
запрещено правилом каноничности: у одного значения обязано быть одно представление.
(Этого в первой редакции не было — пробел нашла независимая реализация декодера.)

Формат — CBOR-подобный: 1 байт тега (старшие 3 бита — мажорный тип, младшие 5 —
короткая длина или маркер расширения), далее varint-длина и полезная нагрузка.

### Правила каноничности (ADR-008) — обязательны

1. Длины кодируются минимальным числом байт.
2. Целые предпочитаются вещественным: `1.0` → int.
3. `-0` кодируется как `0`. `NaN` — единственное представление (`0x7FF8…`).
4. Ключи map сортируются по байтам ключа.
5. Строки — UTF-8, NFC-нормализация **не** применяется (иначе ломается текстовый CRDT).
6. Массивы плотные; `undefined` внутри запрещён (только `null`).

Нарушение любого правила = разные хэши для одного значения = тихий развал сети.

```ts
export function varyEncode(v: Vary): Uint8Array
export function varyDecode(b: Uint8Array): Vary
export function varyEqual(a: Vary, b: Vary): boolean    // по байтам
```

## 5. Тесты

| Тест | Что проверяет |
|---|---|
| `vary.roundtrip.fuzz` | `decode(encode(x)) ≡ x` для 10⁵ значений (fast-check) |
| `vary.canonical.fuzz` | два эквивалентных значения → одинаковые байты |
| `vary.golden` | эталонные векторы из `fixtures/vary.golden.bin` |
| `unit.layout` | офсеты полей соответствуют спецификации |
| `unit.compare` | сортировка соответствует `time ↓, peer ↑, tick ↓` |
| `unit.immutable` | попытка мутации бросает |
| `pack.roundtrip.fuzz` | `encode(decode(b)) ≡ b` побайтово |
| `pack.golden` | `fixtures/pack.golden.bin` |
| `pack.arena` | пакет с зануленными слотами парсится корректно |
| `hash.cross-runtime` | одинаковые хэши в Node и в браузере (CI на обоих) |

Golden-файлы фиксируются **до** первого использования на реальных данных и
меняются только вместе с версией формата.

## 6. Версионирование

Версия формата не хранится в `Pack` (не осталось места и это удорожает каждый
пакет). Вместо этого — в имени субпротокола WebSocket (`sync/1`) и в имени
IndexedDB-базы (`sync-units-v1`). Несовместимая версия = отдельный субпротокол,
отдельная база и явная миграция.

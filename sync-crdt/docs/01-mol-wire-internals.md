# 01. Как устроен $mol_wire под капотом

Разбор по исходникам `../mol/wire/*`. Это не пересказ документации — здесь то,
что видно только в коде, и то, что мы будем переносить.

Файлы-первоисточники:
`wire/wire.ts`, `wire/cursor/cursor.ts`, `wire/pub/pub.ts`, `wire/pub/sub/sub.ts`,
`wire/fiber/fiber.ts`, `wire/atom/atom.ts`, `wire/task/task.ts`,
`wire/sync/sync.ts`, `wire/async/async.ts`, `wire/solo/solo.ts`, `wire/plex/plex.ts`,
`wire/dict/dict.ts`, `wire/set/set.ts`, `wire/solid/solid.ts`, `wire/probe/probe.ts`.

## 1. Иерархия классов

```
$mol_wire_pub          — узел, у которого есть подписчики
└ $mol_wire_pub_sub    — узел, который сам подписывается (умеет трекинг)
  └ $mol_wire_fiber    — + кэш результата + Suspense + планировщик
    ├ $mol_wire_atom   — долгоживущий (аналог computed/signal)
    └ $mol_wire_task   — одноразовый (аналог «действия»)
```

Плюс два вспомогательных: `$mol_wire_dict` / `$mol_wire_set` — обычные `Map`/`Set`,
у которых внутри один `$mol_wire_pub`; любое чтение делает `pub.promote()`, любая
мутация — `pub.emit()`. Гранулярности по ключу нет: изменение одного ключа будит
всех читателей коллекции. Это осознанный размен простоты на точность
(и место, где мы сделаем иначе — см. [02](02-runtime-design.md#reactivemap)).

## 2. Главная оптимизация: один плоский массив на узел

У каждого узла есть `data: unknown[]` — **и аргументы, и зависимости, и подписчики
в одном массиве**:

```
 A1 A2 | P1 p1 P2 p2 P3 p3 | S1 s1 S2 s2
 ^       ^                  ^
 0       pub_from           sub_from
```

- `A*` — аргументы (для `plex`-атомов ключ лежит прямо здесь);
- `P1 p1` — пара «публикатор, **моя позиция в его массиве**»;
- `S1 s1` — пара «подписчик, **моя позиция в его массиве**».

Каждое ребро хранится **дважды, с взаимными индексами**. Следствия:

| | |
|---|---|
| Отписка | `O(1)` — не нужен поиск: позиция известна из пары |
| Память | ~32 B на узел + 8 B на ребро, ноль `Set`/`Map` на узел |
| Удаление из середины | swap-remove через `peer_move`, который чинит обратную ссылку у соседа (`peer_repos`) |

`$mol_wire_pub.sub_off(pos)` переносит последнюю пару на место удаляемой и режет
длину — классический swap-remove, но с починкой обратного индекса. Когда
подписчиков не осталось (`end === sub_from`), вызывается `reap()`.

> Что взять: идею взаимных индексов. Правда, `alien-signals` решает ту же задачу
> двусвязным списком `Link` — по бенчмаркам не хуже, а код проще. См. [ADR-003](00-decisions.md#adr-003).

## 3. Курсор: состояние и позиция в одном поле

```ts
enum $mol_wire_cursor {
  stale = -1,  // нужно пересчитать
  doubt = -2,  // мог измениться кто-то из (транзитивных) публикаторов
  fresh = -3,  // актуален
  final = -4,  // больше никогда не изменится
}
```

Когда `cursor >= 0` — это **позиция в `data`, куда ляжет следующая зависимость**.
То есть одно поле работает и как статус, и как указатель трекинга. Отсюда —
инкрементальный диф зависимостей:

```ts
track_next(pub) {
  const next = this.data[this.cursor]
  if (next === pub) { this.cursor += 2; return next }   // ← совпало: ноль работы
  ...                                                     // не совпало: перекладываем
}
```

**Если пересчёт запросил те же зависимости в том же порядке — не будет ни одной
аллокации и ни одного `sub_on`/`sub_off`.** Это ключ к тому, почему повторные
прогоны файбера (а при Suspense их много) дёшевы.

`track_cut()` в конце отписывается от «хвоста» — зависимостей, которые в этот раз
не были запрошены.

### Двухцветная инвалидация

```
signal изменился
  → emit(stale) прямым подписчикам
      → absorb(stale): cursor = stale, дальше emit(doubt)
          → absorb(doubt): cursor = doubt, дальше emit(doubt)
```

Прямые зависимые становятся `stale`, транзитивные — `doubt`. При чтении
`fresh()` у `doubt`-узла сначала опрашивает свои публикаторы; если ни один
фактически не изменил значение — узел возвращается в `fresh` **без пересчёта**:

```ts
check: if (this.cursor === doubt) {
  for (pub of pubs) {
    pub.fresh()
    if (this.cursor !== doubt) break check   // кто-то реально изменился
  }
  this.cursor = fresh
  return
}
```

Это стандартный glitch-free pull. В `alien-signals` ровно то же самое —
флаги `Dirty` (16) и `Pending` (32) плюс `checkDirty()`.

## 4. Файбер: кэш из трёх состояний

```ts
cache: Result | Error | Promise<Result | Error>
```

Ошибка — **это тоже валидное закэшированное значение**, а не исключение. При
чтении она перебрасывается (`$mol_fail_hidden`). Значит ошибка не пересчитывается
на каждом чтении, а инвалидируется по общим правилам графа. Очень удобно.

`fresh()` в упрощённом виде:

```ts
fresh() {
  if (cursor === fresh || cursor === final) return
  if (cursor === doubt) { /* см. выше */ }

  const bu = this.track_on()          // стать активным подписчиком
  let result
  try {
    result = this.task.call(this.host, ...this.args)
    if (promiseLike(result)) result = wrap(result)   // вернули промис
  } catch (error) {
    result = error instanceof Error || promiseLike(error)
      ? error                          // ← бросили промис = Suspense
      : new Error(String(error))
    if (promiseLike(result)) result = wrap(result)
  }

  if (!promiseLike(result)) this.track_cut()   // ⬅ ВАЖНО
  this.track_off(bu)
  this.put(result)
}
```

### Почему `track_cut()` не вызывается при промисе

Строка `if (!$mol_promise_like(result)) this.track_cut()` — самая важная в файле.
Если файбер приостановился, **список зависимостей не обрезается**: при следующем
прогоне те же зависимости будут запрошены в том же порядке, инкрементальный диф
из §3 их узнает, и пересчёт обойдётся почти бесплатно. Обрезать список означало
бы отписаться от всего и переподписаться заново на каждом шаге ожидания.

### Обёртка промиса

```ts
wrappers.set(result, result = Object.assign(
  result.then(put, put),
  { destructor: result.destructor ?? (() => {}) }
))
const error = new Error(`Promise in ${this}`)
Object.defineProperty(result, 'stack', { get: () => error.stack })
```

Три вещи разом:
1. `WeakMap` дедуплицирует обёртки — один и тот же промис не оборачивается дважды;
2. когда промис разрешится, `put(res)` кладёт значение в кэш и будит подписчиков
   (а для брошенного промиса — `absorb()`, то есть просто инвалидирует);
3. **у промиса подменяется `stack`** на стек места создания — иначе отладка
   Suspense невозможна. Это надо скопировать обязательно.

## 5. Task: как побочные эффекты становятся идемпотентными

Это второй по важности механизм после Suspense и то, чего нет ни в одной
signal-библиотеке.

Файбер могут перезапустить сколько угодно раз (каждое ожидание = перезапуск).
Значит любой `POST /api/order` внутри взорвётся дублями. Решение — `$mol_wire_task`:

```ts
static getter(task) {
  return function (host, args) {
    const sub = $mol_wire_auto()
    const existen = sub?.track_next()          // что лежит на текущей позиции?
    reuse: if (existen) {
      if (!existen.temp) break reuse
      if (existen.task !== task) break reuse
      if (existen.host !== host) break reuse
      if (!compare_deep(existen.args, args)) break reuse
      return existen                            // ← переиспользуем, не выполняем
    }
    return new $mol_wire_task(key, task, host, args)
  }
}
```

Задача опознаётся **по позиции в списке зависимостей родителя** + совпадению
`task`/`host`/`args`. Если при перезапуске код дошёл до той же точки с теми же
аргументами — берётся уже выполненная задача с готовым результатом, тело **не
выполняется повторно**.

Отсюда следуют дисциплины, которые придётся объяснять пользователям:

- порядок вызовов внутри файбера должен быть детерминированным;
- аргументы должны быть сравнимы по значению;
- при расхождении $mol пишет предупреждение `Different task/host/args on restart`
  — мы обязаны сделать то же самое.

Жизненный цикл задачи:

```ts
put(next) {
  if (promiseLike(next)) { cursor = fresh; emit(); return next }
  cursor = final                        // результат получен — навсегда
  if (sub_empty) this.destructor()
  else emit()
}
complete() { if (!promiseLike(cache)) this.destructor() }
```

А `$mol_wire_atom.put()` в конце вызывает `complete_pubs()`, который проходит по
публикаторам и, если **ни один не остался в промисе**, вызывает у всех `complete()`
— то есть **уничтожает все временные задачи разом, когда вся подзадача досчиталась**.
Это и есть «коммит транзакции»: пока не всё готово — задачи живут и хранят
результаты; как только готово — они больше не нужны.

## 6. Границы: sync / async / probe

| Функция | Роль | Механика |
|---|---|---|
| `fiber.sync()` | **провайдер** Suspense | `promote(); fresh();` если кэш — промис или ошибка, то `throw` |
| `$mol_wire_sync(obj)` | обёртка async-API в sync | Proxy: каждый вызов метода → `Task` → `.sync()` |
| `fiber.async()` | **потребитель** Suspense | цикл: `fresh()`; пока кэш — промис, `await Promise.race([cache, step()])` |
| `$mol_wire_async(obj)` | выход в мир промисов | Proxy: вызов → `Task` → `.async()` |
| `$mol_wire_probe(fn)` | чтение без побочек | глобально `warm = false`; файберы возвращают только `result()`, не считают и не подписываются |
| `$mol_wire_stale(fn)` | «отдай старое, пока грузится» | ловит брошенный промис и возвращает предыдущее значение через `probe` |
| `$mol_wire_race(...fns)` | параллельные подзадачи | зовёт все, собирает промисы, бросает `Promise.race` — так N ожиданий идут одновременно, а не последовательно |

### `step()` — как async-цикл узнаёт об инвалидации

```ts
step() {
  return new Promise(done => {
    const sub = new $mol_wire_pub_sub
    const prev = sub.track_on()
    sub.track_next(this)      // временный подписчик на этот файбер
    sub.track_off(prev)
    sub.absorb = () => { done(null); setTimeout(() => sub.destructor()) }
  })
}
```

`await Promise.race([this.cache, this.step()])` просыпается **и** когда
разрешился ожидаемый промис, **и** когда файбер инвалидировали из графа
(например, данные пришли из другого источника и ждать больше нечего). Без этого
`async()` мог бы залипнуть навсегда.

Обрати внимание на `$mol_wire_race`: без него `a(); b();` внутри файбера — это
**последовательные** ожидания (первый `a()` бросит промис, и до `b()` дело не
дойдёт). Это неочевидная ловушка производительности, встроенная в модель.

### 6.1 Поддерживает ли mol `async/await` внутри файберов

Да, но в ограниченном смысле, и это стоит проговорить явно.

**Что работает.** `fresh()` обрабатывает промис, *возвращённый* задачей, ровно
так же, как промис, *брошенный* из неё (`fiber.ts:177` и `fiber.ts:208` — две
почти одинаковые ветки). Значит `async function` как тело файбера легальна:
промис кэшируется, читатель приостанавливается, по разрешению `put(res)` кладёт
значение, и **задача не перезапускается**.

Канонический пример — прямо в `wire/fiber/fiber.test.ts`:

```ts
static async val(a: number) { return a }         // обычная async-функция

static sum(a: number, b: number) {               // sync + Suspense
  const syn = $mol_wire_sync(this)
  return syn.val(a) + syn.val(b)
}

static async calc(a: number, b: number) {        // граница наружу
  return 5 + await $mol_wire_async(this).sum(a, b)
}
```

**Что не работает — отслеживание зависимостей после первого `await`.**
`$mol_wire_auto` меняется по дисциплине стека: `track_on()` перед вызовом,
`track_off(bu)` сразу после возврата. `async`-функция возвращает управление уже
на первом `await`, поэтому всё, что читается в продолжении, выполняется в
микрозадаче с уже снятым активным подписчиком — молча, без подписки.

**Как следствие — негласная конвенция:** `async` только на листовых операциях
(`Task`), никогда на реактивных каналах (`Atom`). Проверяется эмпирически:

```
$ grep '@ $mol_mem…' + следующая строка 'async'  в mam_mol и baza  →  0 совпадений
```

Единственный `async` под декоратором во всём mol — под `$mol_memo.method`
(`crypto2/signer/signer.ts:23`), а это нереактивный мемо по аргументам, он вообще
не собирает зависимости.

А в baza есть прямая иллюстрация обходного приёма — `land.ts:1212`:

```ts
async units_sign(units) {
  await Promise.resolve() // prevent deps
```

Пустой `await` в первой строке нужен именно для того, чтобы зависимости **не**
собрались.

**Цена перезапусков видна в тесте `Idempotence control`** (там же в `fiber.test.ts`):
`sum()` выполняется три раза (первый заход + после разрешения каждого из двух
промисов), и поэтому

```
log_idemp   (под @ $mol_wire_method → Task)  → 1 вызов
log_unidemp (обычный вызов)                  → 3 вызова
```

Это лучшая однострочная демонстрация того, зачем вообще нужен `Task`.

Вывод для нас: правило переносим, но делаем его **проверяемым типами**, а не
устной договорённостью — см. [02 §4.1](02-runtime-design.md#41-async-функции-внутри-файберов).

## 7. Планировщик и сборка мусора

```ts
plan()   → planning.add(this);  $mol_after_tick(() => sync())
reap()   → reaping.add(this);   $mol_after_tick(...)   // вызывается когда ушёл последний sub

static sync() {
  while (planning.size) { for (f of planning) { planning.delete(f); f.fresh() } }
  while (reaping.size)  { for (f of reaping)  { if (f.sub_empty) f.destructor() } }
}
```

- Одна микрозадача (`Promise.resolve().then`) на весь тик, а не по одной на узел.
- **GC автоматический и немедленный**: атом без подписчиков уничтожается в конце
  тика. Не нужно ни `gcTime`, ни ручных `dispose` — «живо то, что кто-то читает».
- `$mol_wire_solid()` подписывает узел на вечно живущий фиктивный `sub` и
  подменяет `reap` на no-op — так «пиннят» корневые объекты (ленды, сокеты).

Это принципиально отличается от `effectScope` в Vue/alien-signals, где время
жизни привязано к скоупу компонента. Здесь — к достижимости из графа чтения.
Для нашей задачи это ровно то, что нужно: ленд жив, пока на него смотрит хоть
один компонент.

## 8. Каналы без магии

`$mol_mem` — это `$mol_wire_solo`, декоратор, который подменяет метод на:

```ts
function (...args) {
  const atom = $mol_wire_atom.solo(this, orig)
  if (args.length === 0 || args[0] === undefined) {
    if (!warm) return atom.result()
    return $mol_wire_auto()?.temp ? atom.once() : atom.sync()
  }
  return atom.resync(args)     // запись
}
```

- атом хранится **прямо на хосте** в поле `имя()` (или в `Map` для `plex`);
- `$mol_mem_key` (`plex`) — то же, но `Map` по `$mol_key(args[0])`;
- деталь: если читатель — временная задача (`sub.temp`), используется `once()`
  вместо `sync()`, чтобы задача не стала долгоживущим подписчиком;
- `resync()` перед записью **убивает все дочерние `Task`** — «отменить всё, что
  сейчас грузится, я задаю новое значение».

`$mol_wire_field` — то же для геттеров/сеттеров свойств.

## 9. Итог: что берём, что нет

| Механизм | Берём? | Комментарий |
|---|---|---|
| Взаимные индексы рёбер | 🔁 | берём идею, реализацию — из `alien-signals/system` |
| Курсор как позиция трекинга | ✅ | в `alien-signals` это `depsTail` + `version` |
| stale/doubt + `checkDirty` | ✅ | есть в `alien-signals` из коробки |
| `cache: Result \| Error \| Promise` | ✅ | ядро нашей модели |
| `throw Promise` как Suspense | ✅ | |
| Не резать зависимости при Suspense | ✅ | **обязательно**, иначе всё разваливается |
| Подмена `stack` у промиса | ✅ | без этого отладка невозможна |
| `Task` с позиционным переиспользованием | ✅ | идемпотентность эффектов |
| `complete_pubs()` как коммит | ✅ | |
| `sync()` / `async()` / `step()` | ✅ | |
| `probe` (`warm = false`) | ✅ | нужен для devtools и `stale` |
| `race()` | ✅ | иначе параллелизм не выразить |
| Микрозадачный планировщик + reaping | ✅ | |
| `solid()` | ✅ | под именем `pin()` |
| Хранение атома в поле хоста `имя()` | ❌ | грязно; у нас — `WeakMap` |
| Декораторы | ❌ | `erasableSyntaxOnly`; фабрики `solo()`/`plex()` |
| Proxy-обёртки `$mol_wire_sync(obj)` | ⚠️ | оставим, но добавим явную форму `sync(fn, ...args)` — Proxy плохо типизируется и мешает tree-shaking |
| Коллекции с одним `pub` на всю карту | ❌ | делаем гранулярность по ключу |
| `$mol_wire_auto` как глобал модуля | ✅ | это дисциплина стека вызовов, мультиэкземплярности не мешает |

## 10. Честный список опасностей модели

Их надо принять сознательно — они не баги, а цена подхода.

1. **Всё внутри файбера должно быть перезапускаемым.** Любой эффект мимо `Task`
   выполнится N раз. Нужен dev-warning и правило линтера.
2. **Последовательность вместо параллелизма по умолчанию.** Два независимых
   ожидания в одном файбере выполнятся друг за другом, если не обернуть в `race()`.
3. **Стек-трейсы.** Между «где упало» и «кто ждал» — граница промиса. Спасает
   только подмена `stack` и `id` у каждого файбера.
4. **`try/catch` вокруг Suspense обманчив.** Брошенный промис — не ошибка, но
   пользовательский `catch (e) {}` его проглотит и всё сломает. Нужен
   `isSuspend(e)` в публичном API и предупреждение в доке.
5. **Мутация внутри чтения запрещена.** `$mol_wire_pub_sub.promote()` кидает
   `Circular subscription`, если узел читают во время его же пересчёта.
6. **Сравнение аргументов задач — `compare_deep`.** На больших объектах это
   дорого; ключи задач надо держать примитивными.

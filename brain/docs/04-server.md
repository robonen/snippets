# brain · сервер синхронизации

> **Статус: работает.** Сервер (`apps/server/`, пакет `@brain/server`), кодек кадров
> (`packages/sync-wire`), клиент (`apps/web/src/sync`) и кран сундука
> (`module-kit/tapped-chest.ts`) написаны и проверены живьём: заметка уехала
> шифртекстом, стёртый кэш восстановился с сервера, выключенный сервер ничего
> не сломал.
>
> Читать вместе с [01-security.md](01-security.md): границы того, что сервер
> видит, заданы там (У2), здесь — как он устроен и как его поднять у себя.

## 0. Главное, из чего всё следует

**Сервер — не пир CRDT, а слепой хранитель журнала.** У kcal сервер поднимал
ленд и гонял `exchange()` по открытым байтам — мог, потому что байты были
открыты. В brain ленды запечатаны на устройстве: у сервера нет ключа, и он не
должен его иметь (01-security, У2). Значит, серверу нечем ни слить две правки,
ни отличить дельту от мусора — и он этого не делает. Всё серверное состояние
ленда — **append-only журнал запечатанных кусков**, ровно тех, что клиент
держит в своём сундуке (`module-kit/sealed.ts`): `nonce(12) || cipher`,
непрозрачные байты.

**Слияние остаётся на клиентах, и сходимость даётся бесплатно.** Каждый кусок —
валидная пачка CRDT; применение идемпотентно, порядок неважен. Отсюда весь
протокол: «дочитай куски, которых не видел, дошли куски, которых не видел
сервер» — из любого состояния, сколько угодно раз. Любое сомнение — счётчики
разошлись с журналом, сервер сжался за спиной — лечится перечитыванием с нуля:
это всегда безопасно и никогда не теряет.

**Один инстанс — предусловие, а не ограничение.** Личное пространство живёт на
одном своём сервере. Поэтому очередь на ленд — внутри процесса (`withLand`,
тот же lost-update-довод, что у kcal), хранилище — файлы через unstorage
fs-драйвер, и никакого Redis: второй инстанс здесь не появится, а городить
координацию под несуществующий — работа против себя.

## 1. Журнал на диске

```
DATA_DIR/
  head/<land>            «<поколение>:<число кусков>» — единственная истина
  chunk/<land>/<g>/<n>   кусок n поколения g
```

Журнал определяется головой: живо только поколение, которое она называет.
Компакция (`REPLACE`) атомарна без переименований, которых у unstorage нет:

1. новый кусок пишется в **следующее** поколение — старый журнал не тронут;
2. голова переписывается одной маленькой записью — **точка фиксации**;
3. куски прежнего поколения убираются.

Обрыв до шага 2 — журнал прежний (клиент не получил ответа и повторит); обрыв
после — журнал новый, а осиротевшие куски выметает `sweep` при первом касании
ленда после старта. Терять журнал негде; оба обрыва проиграны в
`server/utils/journal.test.ts` на настоящей файловой системе.

Удаления в протоколе **нет**: сервер append-only, забыть журнал может только
хозяин железа — `rm -r $DATA_DIR/chunk/<land> $DATA_DIR/head/<land>` при
остановленном сервере (или `Journal.wipe` из своего скрипта). Бэкап всего
состояния — копия каталога `DATA_DIR`.

## 2. Транспорт 1 — WebSocket, один на все ленды

Одно соединение на устройство: адрес ленда лежит в каждом кадре, а не в URL
(план, Р7). Кадры бинарные — полезная нагрузка и так шифртекст. Кодек —
`packages/sync-wire`, единый для клиента и сервера.

```
[op:1][land:11 ascii base64url][payload]

op  имя      кто→кому  payload
01  HELLO    c→s       have:u32be   «я видел have кусков — дошли остальные»
02  CHUNK    s→c       index:u32be, bytes
03  APPEND   c→s       bytes        дописать кусок в хвост
04  HEAD     s→c       count:u32be  голова журнала (ответ на 01, 03, 05)
05  REPLACE  c→s       ifHead:u32be, bytes   компакция, если голова == ifHead
06  REJECT   s→c       head:u32be   замена не состоялась
```

Подключение: `wss://host/sync?token=…` — токен в query, потому что браузерный
WebSocket не умеет ставить свои заголовки на рукопожатие.

Семантика на сервере (`server/routes/sync/index.ts`):

- **HELLO** подписывает соединение на ленд и отвечает кусками `[have..head)`
  плюс `HEAD(head)`. `have` больше головы — клиент видел журнал, которого
  больше нет (чужая компакция): сервер отдаёт всё с начала, клиент перечитывает
  — идемпотентно.
- **APPEND** дописывает, отвечает `HEAD` и вещает `CHUNK` остальным
  подписчикам ленда (`peer.publish` — отправителю эха нет).
- **REPLACE** — оптимистичная компакция: голова совпала — журнал стал одним
  куском (`HEAD(1)`), нет — `REJECT(head)`, и клиент живёт дальше. Успешная
  замена не вещается: заменить журнал мог только клиент, видевший его целиком,
  — остальным в этом куске нет ничего нового, а отставшие заметят смену головы
  приветом.
- Мусор — обрезанный кадр, чужой op, кривой адрес, кусок короче нонса с меткой
  GCM — молчаливый отказ, не исключение и не разрыв соединения.

### Инварианты клиента (`apps/web/src/sync/engine.ts`)

На устройстве два счётчика на ленд, в localStorage рядом с `brain.peer`:
`seen` — влитый **префикс** кусков сервера, `uploaded` — сколько кусков
местного журнала отправлено.

- На коннекте — `HELLO(seen)`; досылка своего `[uploaded..)` ждёт `HEAD`.
- Перед приветом счётчики сверяются с сундуком: **пустой журнал при ненулевых
  счётчиках означает «кэш шифртекста потерян, ключи целы»** — счётчики
  сбрасываются, и сервер отдаёт всё с нуля. Это главный сценарий
  восстановления, он проверен живьём.
- `seen` растёт только сплошным префиксом: кусок, который не расшифровался
  (чужой DEK до Э2, порча), оставляет счётчик на месте — его перечитают, когда
  появится нужная обёртка.
- Компакция местного журнала шлёт `REPLACE`, только когда `seen == head` —
  иначе (и на `REJECT`) тот же кусок уходит обычным `APPEND`: сервер
  подрастает, но сходится.
- **Эхо не страшно**: кусок, влитый с сервера, попадает в местный журнал
  (писатель сохраняет услышанное) и один раз уезжает обратно `APPEND`-ом.
  Повторное применение идемпотентно, на втором круге изменений нет — петля
  гаснет. Фильтр происхождения не строится намеренно.

Реконнект — с отступами 1 → 2 → 5 → 10 → 30 с; обрыв — норма, наш код в
консоль не пишет (браузер свой нативный лог о неудавшемся коннекте пишет сам,
это не отключается).

## 3. Транспорт 2 — HTTP-фолбэк

Та же семантика без сокета — для сред, где WebSocket не проходит, и для
скриптов. Токен — заголовком `authorization` (`Bearer` не обязателен).

```
GET  /sync/:land?from=N     тело: повторяющиеся [len:u32be][chunk],
                            голова — заголовком x-head
POST /sync/:land            тело — кусок; ответ { head }
POST /sync/:land/replace?if=N   200 { head: 1 } либо 409 { head }
```

```sh
curl -H "authorization: Bearer $TOKEN" "https://host/sync/a2NhbGtjYWw?from=0" -o tail.bin
curl -H "authorization: Bearer $TOKEN" --data-binary @chunk.bin "https://host/sync/a2NhbGtjYWw"
```

Вещания у POST нет: подписки живут на сокете, а клиенты фолбэка добирают
опросом — журнал закрывает пропуск сам.

## 4. Клиентская сборка

- **Кран сундука** (`module-kit/tapped-chest.ts`) — декоратор над `Chest`:
  сообщает «дописан кусок №n» и «журнал заменён» ПОСЛЕ успеха носителя. Синк
  узнаёт о кусках здесь — не трогая ни ключ, ни открытую пачку.
- **Движок** (`apps/web/src/sync/`) живёт между снятием замка и его закрытием
  (`boot.ts`): без ключа принятые куски нечем распечатать. Принятая пачка
  вливается в живой ленд тем же путём, что и пачка соседней вкладки, —
  `packDecode` + `land.apply`.
- **Настройки** — карточка «Синхронизация» на экране настроек: адрес и токен в
  localStorage. Токен — секрет устройства, в ленд ему нельзя: ленд уезжает на
  тот самый сервер. Пусто — синк выключен, приложение полностью local-first.
- **Мета-ленд не синхронизируется**: обёртки ключа на сервер не ездят
  (01-security §2). Честное следствие — второе устройство пока подключиться не
  может: у него свой DEK, чужие куски оно не расшифрует. Обмен обёртками —
  отдельный шаг Э2. Сегодняшняя ценность сервера: внешняя копия шифртекста
  («кэш потерян, ключи целы» — восстановление) и готовый транспорт.

## 5. Запуск на своём сервере

Никакого Vercel: обычный node-server.

```sh
cd brain
pnpm install
pnpm --filter @brain/server build     # nitro build → apps/server/.output
SYNC_TOKEN=… DATA_DIR=/var/lib/brain PORT=8787 \
  node apps/server/.output/server/index.mjs
```

| env | что | по умолчанию |
|---|---|---|
| `SYNC_TOKEN` | общий секрет; **без него сервер отказывает всем** | — |
| `DATA_DIR` | каталог журналов; читается на рантайме | `./data` |
| `PORT` | порт node-server | `3000` |

systemd-юнит (`/etc/systemd/system/brain-sync.service`):

```ini
[Unit]
Description=brain sync server
After=network.target

[Service]
User=brain
WorkingDirectory=/opt/brain
ExecStart=/usr/bin/node /opt/brain/apps/server/.output/server/index.mjs
Environment=PORT=8787
Environment=DATA_DIR=/var/lib/brain
EnvironmentFile=/etc/brain/sync.env   ; здесь SYNC_TOKEN=…
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

nginx перед ним — обязательно с проксированием WebSocket: без `Upgrade` и
`Connection` рукопожатие сокета молча превращается в обычный GET.

```nginx
server {
    listen 443 ssl http2;
    server_name brain.example.com;
    # ssl_certificate …; ssl_certificate_key …;

    location /sync {
        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 1h;      # тихий сокет — не мёртвый сокет
    }
}
```

В приложении: Настройки → Синхронизация → `https://brain.example.com` и тот же
токен. Дев-режим: `SYNC_TOKEN=dev DATA_DIR=/tmp/brain-data pnpm --filter
@brain/server dev`.

## 6. Чего здесь не делать

- **Не поднимать ленд на сервере** — ключа нет, и появиться он там не должен;
  «умный» сервер означал бы конец E2E.
- **Не хранить распакованное** и не заводить REST по сущностям — те же доводы,
  что закрыли это у kcal, плюс шифрование: серверу нечего распаковывать.
- **Не добавлять второй инстанс с общим `DATA_DIR`** — очередь на ленд живёт в
  процессе; двум процессам нужен лок, которого нет намеренно.
- **Не чистить журналы «по хозяйству»** из кода — удаление только руками
  хозяина (§1): протокол append-only, и клиенты вправе на это полагаться.

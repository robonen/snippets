# brain · сервер синхронизации — ревизия 3

> **Статус: работает.** Сервер (`apps/server/`) — **обычный пир ядра
> `@sync/core`** над юнитами с запечатанным payload. Прежний слепой
> append-only журнал с поколениями, компакцией и собственным кадровым
> протоколом (`@brain/sync-wire`) упразднён: его работу делает сам протокол
> ядра, потому что шифрование переехало на уровень юнита
> ([01-security.md](01-security.md) §3).

---

## 0. Главное, из чего всё следует

**Слияние работает на шифртексте.** LWW читает только заголовки юнитов, а они
открыты; payload запечатан ключами, которых на сервере нет. Значит серверу не
нужен ни ключ, ни собственный протокол — он гоняет тот же `Land.apply` /
`diffOf`, что и браузер:

- **кадр = пачка формата ядра** (адрес ленда в заголовке секции; одно
  WS-соединение мультиплексирует все ленды);
- **привет** = фейсы клиента → ответ = дельта сервера + его фейсы → клиент
  считает встречную дельту и досылает своё;
- **правка** = пачка собственных юнитов клиента (кран ленда) → сервер
  применяет и вещает соседям по ленду (`peer.publish`, эха себе нет).

Любой обрыв, потеря и рестарт закрываются следующим приветом: доставка
идемпотентна, «непереданное» — это дельта от фейсов, отдельных счётчиков
прогресса нет ни у клиента, ни у сервера.

**Персист ленив — и это безопасно.** Образ ленда пишется одним куском с
отложкой (1 с после последнего изменения, плюс на остановке процесса). Упавший
между приёмом и записью сервер ничего не теряет: клиент хранит всё локально и
дошлёт по фейсам. Диск сервера — кэш, а не единственная копия; поэтому нет ни
журнала, ни поколений, ни атомарной смены голов.

**Один инстанс — предусловие.** Личное пространство на одном сервере: хаб
живёт в памяти процесса, хранилище — файлы.

## 1. Устройство

```
routes/sync.ts            WS: авторизация рукопожатия, подписки, доставка
routes/lands/[land].delete.ts  админ-ручка отзыва: забыть ленд (токен)
routes/[...path].get.ts   SPA-фолбэк (index.html из кэша процесса)
plugins/storage.ts        рантайм-маунт data: (Cloudflare KV | DATA_DIR) + flush на close
utils/hub.ts              вся логика: ленды, exchange, вещание, персист
utils/instance.ts         хаб процесса над useStorage('data')
utils/auth.ts             токен: чистая timing-safe проверка
utils/config.ts           типизированный runtimeConfig (SYNC_TOKEN, PUBLIC_ORIGIN, DATA_DIR)
```

Идиомы nitro v3: `defineConfig` из `nitro/config`; `runtimeConfig` +
`useRuntimeConfig` для `SYNC_TOKEN`/`PUBLIC_ORIGIN`/`DATA_DIR` (имена плоские —
`envPrefix: ''`, `NITRO_`-префикс работает второй дорогой); `storage`/
`devStorage` в конфиге как статичное умолчание и `definePlugin` +
`useStorage().mount()` как рантаймовое переопределение `DATA_DIR` — ровно по
документированной схеме; `defineHandler` (`event.req` — нативный `Request`),
`defineWebSocketHandler` (crossws: `peer.subscribe`/`publish`). Хаб получает
хранилище через DI и гоняется vitest'ом без nitro (`utils/hub.test.ts`).

Хранилище: `head:`/`chunk:`-раскладки больше нет — по ключу `land:<адрес>`
лежит один образ (валидная пачка ядра), по ключу `peer` — пир сервера
(8 случайных байт, стабилен между рестартами ради фейсов).

## 2. Что сервер видит и чего не может

Видит: заголовки юнитов (кто, когда, в какой узел), число юнитов, времена
обращений — метаданные из [01-security.md](01-security.md) §1. Не может:
прочитать payload (ключей нет); подменить payload незаметно (AAD+GCM на
устройстве); подсунуть юнит одного ленда другому (адрес ленда в связке нонса).
Подделку заголовков ловят подписи этапа 2 — до них сервер под токеном считается
честным по доступности, но не по конфиденциальности.

Удаление — только явной админ-ручкой `DELETE /lands/:land` (токен): она нужна
отзыву устройства (перепечатанный ленд заливается с нуля) и хозяину железа.

## 3. Запуск на своём сервере

```sh
cd brain
pnpm install
pnpm --filter @brain/web build       # PWA с service worker
pnpm --filter @brain/server build    # nitro build → apps/server/.output
SYNC_TOKEN=… DATA_DIR=/var/lib/brain PORT=8787 PUBLIC_ORIGIN=https://brain.example.com \
  node apps/server/.output/server/index.mjs
```

| env | что | по умолчанию |
|---|---|---|
| `SYNC_TOKEN` | общий секрет; **без него сервер отказывает всем** | — |
| `DATA_DIR` | каталог образов (файловое хранилище) | `./.data` |
| `CLOUDFLARE_KV_ACCOUNT_ID` | продакшен-хранилище: Cloudflare KV по REST | — |
| `CLOUDFLARE_KV_NAMESPACE_ID` | — вместе с account id | — |
| `CLOUDFLARE_KV_API_TOKEN` | токен с правом Workers KV Storage: Edit | — |
| `PUBLIC_ORIGIN` | origin для сверки `Origin` на WS-рукопожатии | `http://localhost:4877` |
| `PORT` | порт node-server | `3000` |

**Продакшен-хранилище — Cloudflare KV.** Заполнены все три `CLOUDFLARE_KV_*`
— плагин перемонтирует `data:` на `cloudflare-kv-http` (REST, сервер остаётся
node-процессом; `DATA_DIR` тогда не нужен). Образы едут строками
`base64:…` — это штатный raw-фолбэк ядра unstorage, хаб разницы не видит
(тест «профиль cloudflare-kv-http»). Эвентуальная консистентность KV не
угрожает по построению: истина — память единственного процесса, KV — ленивый
снапшот, отставший после рестарта образ долечивает первый же привет клиента по
фейсам. Лимит значения KV — 25 МиБ на ленд: личному пространству хватает с
запасом.

systemd и nginx — как раньше (проксирование WebSocket с `Upgrade`/`Connection`
обязательно); маршруты `/auth` и `/account` исчезли, наружу торчат `/sync`
(WS), `/lands/:land` (DELETE) и статика PWA.

В приложении: Настройки → Синхронизация → адрес и тот же токен. Пусто — синк
выключен, приложение полностью local-first.

## 4. Чего здесь не делать

- **Не давать серверу ключи** — «умный» сервер означал бы конец E2E; слияние и
  так работает.
- **Не заводить REST по сущностям** — серверу нечего распаковывать.
- **Не добавлять второй инстанс с общим `DATA_DIR`** — хаб живёт в процессе.
- **Не «чинить» данные на сервере** — образ можно стереть (`DELETE`), починит
  его первый же привет клиента.
